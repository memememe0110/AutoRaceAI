# AutoRaceAI 日時処理ルール

## 1. 目的

日時の保存形式・比較方法・表示方法が機能ごとに混在し、9時間の表示ずれや時系列ソートの逆転が発生することを防ぐ。

この文書は、現時点で確認できた既存実装を維持しながら、今後の機能追加で守るルールを定める。既存データの一括変換や既存コードの一斉変更を指示するものではない。

## 2. 保存ルールは新規列と既存列の2層に分ける

### 2.1 新規追加する日時列

新たに日時列を追加する場合は、原則として **UTC naive のISO 8601形式** で保存する。

- 保存値のタイムゾーン契約はUTCとする。
- naiveであることを理由に、任意のローカル時刻として解釈してはならない。
- 書き込み側・読み込み側の双方で、UTCとして扱うことを明示する。
- 例: `2026-11-15T16:49:08`（UTC）

### 2.2 既存日時列

既存列は、列ごとに確認済みの現在の保存形式を維持する。新規列のルールを理由に、既存列の書き込み形式を変更しない。

| テーブル・列 | 現在確認できている形式 | 扱い・確度 |
|---|---|---|
| `result_races.registered_at` | UTC naive ISO相当 | UTCとして扱う |
| `v223_result_view_restore.updated_at` | JST offset付きISO | JST offset付きの現行仕様を維持 |
| `v231_prediction_history.prediction_time` | JST offset付きISO | JST offset付きの現行仕様を維持 |
| `player_lap_history.created_at` | naive日時文字列 | タイムゾーン未確定。UTCと断定しない |
| `v41_registration_batches.registered_at` | naive ISO日時文字列 | UTC濃厚だが確定扱いしない |

形式が似ていることだけを根拠に、未確定列のタイムゾーンを推定してはならない。保存形式・生成元・実測値を確認してから列単位で確定する。

## 3. 確認済みの時刻帯実測記録

川口1R（race_key: `20261114_川口_1R`）の登録時刻について、次の対応を確認した。

| 項目 | 値 |
|---|---|
| `result_races.registered_at` の保存値 | `2026-11-15T16:49:08` |
| UTCとして解釈した時刻 | 2026-11-15 16:49:08 UTC |
| 画面表示 | 2026-11-16 01:49:08 JST |

保存値と画面表示は同一時刻を表し、日付をまたぐ9時間差で整合する。この実測を `result_races.registered_at` をUTC naiveとして扱う根拠の一つとする。

この実例を、他の日時列のタイムゾーン判定に流用してはならない。

## 4. 日時の比較・ソート

日時の実時刻を比較・ソートする場合、タイムゾーンを明示的に解決したうえで、日時として正規化して比較する。日時文字列の辞書順比較を実時刻比較の代用にしてはならない。

- SQLite SQLでは、列の保存契約を確認したうえで `julianday()` 等を使用し、同一の時間軸に正規化する。
- Python等のアプリケーションコードでは、列の保存契約に従ってタイムゾーンを解決し、`parse_iso()` 等で正規化して比較する。
- UTC naiveは、この文書でUTCと確定した列に限りUTCとして解釈する。
- JST offset付き日時は、offsetを保持したまま実時刻に正規化する。
- タイムゾーン未確定のnaive日時は、推測でUTCまたはJSTを付与せず、比較対象に使う前に仕様を確認する。
- `NULL`、空文字、不正な日時の扱いを明示し、欠損値を実時刻として扱わない。

文字列比較の禁止は日時値に対するものとする。`race_key` 等の識別子や、日時ではない固定形式文字列の比較には適用しない。

### SQLite利用時の注意

SQLiteの `julianday()` は、タイムゾーン情報のない日時をUTCとして扱う。したがって、UTC naive列とoffset付き日時の混在比較には利用できるが、JSTローカル時刻をoffsetなしで保存した値やタイムゾーン未確定値に無条件で適用してはならない。列ごとの保存契約を確認すること。

## 5. 画面表示

画面に日時を表示する場合は、表示仕様に従ってJSTへ変換する。

- 保存値をそのまま画面に出さない。
- 既存の保存結果時刻表示では `_v228_format_saved_time()` を使用する。
- offset付き日時を変換する際は、元のoffsetを尊重してからJSTへ変換する。
- タイムゾーン未確定値は、確定したかのようにJST表示へ変換しない。必要に応じて未確定であることを明示する。

## 6. 共通日時関数の候補（将来構想・未実装）

日時処理を一元化するため、将来的に次のような共通関数を検討する。

- `_now_utc()`: UTC現在時刻の取得
- `_now_jst()`: JST現在時刻の取得
- `_to_utc()`: タイムゾーンが確定した日時をUTCへ変換
- `_to_jst()`: タイムゾーンが確定した日時をJSTへ変換
- `_parse_datetime()`: 列の保存契約に従った日時解析

これらは候補名であり、**今回の文書追加では実装しない**。既存の `_v228_now_jst_iso()` や `_v228_format_saved_time()` の挙動も変更しない。

## 7. 必須テストケース

日時列の追加・日時処理の変更・日時を使う検索やソートの変更では、変更内容に応じて少なくとも次のケースをテストする。

1. **UTCとJSTの同一時刻**: UTC naiveとJST offset付きの値が同一時刻を表す場合、同じ時刻として扱われる。
2. **混在値の時系列ソート**: UTC naiveとoffset付き日時が混在しても、実時刻順に並ぶ。NULL等の欠損値の順序も明示する。
3. **日付またぎ**: JSTの23:59と翌日00:01を含む検索・集計で、日付境界を誤らない。
4. **naive日時の契約**: UTCと確定した列だけをUTCとして解釈し、タイムゾーン未確定値を推測で補完しない。
5. **夏時間のある外部データ**: 外部データのタイムゾーンと夏時間を考慮し、offsetまたは地域タイムゾーンに基づいて正規化する。
6. **欠損・不正値**: NULL、空文字、不正な日時が比較・ソート・表示で誤った実時刻として扱われない。

SQLiteの `julianday()` を使う場合は、UTC naiveとして扱う列とoffset付き日時の組み合わせ、およびNULLの扱いを含めてテストする。
